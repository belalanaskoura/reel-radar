# Build history

Full, verbatim development history for ReelRadar — every phase's detailed
notes and every post-launch follow-up session, including bugs found, how
things were verified, and dead ends. This is the source material
`CLAUDE.md` summarizes; nothing here contradicts `CLAUDE.md`, it just has
the full story `CLAUDE.md` compresses out to stay short.

`CLAUDE.md` is the one auto-loaded every session and stays lean on
purpose. Read this file when you need the *why* behind something
`CLAUDE.md` only mentions in passing, or when picking up a thread that
was only briefly summarized there.

## Phase 2 notes (DONE)

- Scaffolded with `create-next-app` (Next.js 16, App Router, TypeScript,
  Turbopack, no Tailwind, `src/` dir). Note: scaffolding a non-empty repo
  overwrites `README.md`/`.gitignore` and drops stub `CLAUDE.md`/`AGENTS.md`
  files — see "tooling gotchas" below. `AGENTS.md` is regenerated by
  `next dev` on every run and is now gitignored rather than fought.
- Supabase project created (`ezckygwfbodsjfhfsseg`). Schema applied via
  the SQL Editor (not CLI — no DB password was linked, just the
  publishable/secret API keys) as two migration files in
  `supabase/migrations/`: `0001_initial_schema.sql` (branches, movies,
  movie_branch_slugs, showtimes_cache, watchlist, notification_log — as
  designed in Phase 1) and `0002_add_movie_popularity.sql`, a follow-up
  that adds `movies.popularity` (numeric, from TMDB) — added after
  noticing during testing that storing popularity will matter for Phase 5
  matching/disambiguation and Phase 7 sort/display, and it's cheaper to
  add now than re-migrate later.
- `branches` table is seeded directly in the migration (`cfc`,
  `district5`) rather than via a job — static reference data.
- TMDB integration lives in `src/lib/tmdb.ts`
  (`fetchUpcomingMovies(fromDate, toDate)`), applying the Phase 0 findings
  directly: `region=EG` alone is not a real filter, so it's combined with
  `sort_by=popularity.desc` and `with_release_type=2|3`; paginates up to 5
  pages (100 movies) per run.
- Sync job is `POST /api/sync-movies` (`src/app/api/sync-movies/route.ts`),
  guarded by an `x-sync-secret` header checked against `SYNC_SECRET` (env
  var) — same pattern the Phase 1 architecture calls for on `/api/poll`
  later, proven out here first. Upserts on `tmdb_id` so re-running is
  idempotent (verified: re-ran after adding the popularity column, row
  count stayed at 100, no duplicates, popularity backfilled correctly).
- `src/lib/supabase.ts` (moved to `src/lib/supabase/service-role.ts` in
  Phase 3, see below) exports `createServiceRoleClient()` — server-only,
  bypasses RLS, must never be imported into client components.
- Verified end-to-end against the live Supabase project: synced 100 real
  upcoming movies, spot-checked known high-popularity titles (Avengers:
  Doomsday, Ramayana, The Last Sunrise) landed correctly with correct
  dates and no nulls.
- Env vars in play (see `.env.example`): `NEXT_PUBLIC_SUPABASE_URL`,
  `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`,
  `TMDB_API_KEY`, `SYNC_SECRET`. `.env.local` holds real values and is
  gitignored; `.env.example` is tracked with blank values.
- Not yet done, deliberately deferred to later phases: no Scene scraping
  (Phase 4), no TMDB-to-Scene slug matching (Phase 5), no RLS policies on
  `watchlist`/`notification_log` (Phase 3, once auth.users rows exist to
  scope against).

## Phase 3 notes (DONE)

- Auth uses `@supabase/ssr` (cookie-based session, current recommended
  approach for Next.js App Router — not the older auth-helpers package).
  Three Supabase client variants now exist in `src/lib/supabase/`:
  `client.ts` (browser client, not yet used by any component — all auth
  so far goes through server actions), `server.ts` (cookie-aware, RLS-
  respecting, used in server components/route handlers/server actions),
  and `service-role.ts` (the Phase 2 service-role client, moved here from
  `src/lib/supabase.ts` for consistency — bypasses RLS, server-only).
- Session refresh lives in `src/proxy.ts` (not `middleware.ts` — Next.js
  16 renamed the convention to "proxy" mid-way through this phase; the
  export is `proxy`, not `middleware`, everything else about it is
  unchanged). Delegates to `src/lib/supabase/middleware.ts`'s
  `updateSession()`.
- Schema: `supabase/migrations/0003_auth_profiles_and_rls.sql` adds a
  `profiles` table (`id` referencing `auth.users`, `ntfy_topic` unique
  nullable text) plus a trigger (`handle_new_user`) that inserts a profile
  row automatically on signup, so the app never has to special-case a
  missing profile. Also turns on RLS: `profiles`/`watchlist` scoped to
  `auth.uid()`; `notification_log` is user-readable but only
  service-role-writable (the poll job in Phase 6 will write it, bypassing
  RLS); `movies`/`branches`/`movie_branch_slugs`/`showtimes_cache` are
  publicly readable (signed-out visitors can browse) but not writable
  except via service role.
- Pages: `/signup`, `/signin` (email+password, matching the Phase 1
  decision to skip OAuth), `/account` (shows signed-in email, a form to
  set `ntfy_topic`, and sign-out) — all server components using server
  actions (`src/app/{signup,signin,account}/actions.ts`) rather than
  client-side fetch calls. `/account` redirects to `/signin` if there's
  no session. Home page (`/`) shows signed-in-state vs. sign-in/sign-up
  links — still a placeholder for Phase 7's real browse/watchlist UI.
- Unique-`ntfy_topic` collisions are caught by Postgres error code
  `23505` and surfaced as a specific "already taken" message rather than
  a raw DB error — verified this fires correctly with two real accounts
  colliding on the same topic.
- Turned OFF Supabase's "Confirm email" setting (Authentication →
  Providers → Email) for faster local iteration — signup now returns an
  active session immediately instead of requiring an email click.
  **Must be turned back on before Phase 8 (production/real users)** —
  tracked here so it isn't forgotten.
- Verified directly against the live Supabase project (not just
  typecheck/build): real signup creates a session and a profile row;
  updating one's own `ntfy_topic` succeeds under RLS; an unauthenticated
  client reading another user's profile gets an empty result (RLS filters
  silently, doesn't error); topic collision produces the expected `23505`.
  Also manually clicked through the full browser flow (signup → account
  settings save → sign out → sign in) to confirm the UI itself, not just
  the backend logic, works.
- Not yet done, deferred to later phases: no watchlist UI (Phase 7), no
  password reset/forgot-password flow (not in scope per the original
  plan — can be added later if needed), browser Supabase client
  (`client.ts`) exists but is unused until a client component needs it.

## Phase 4 notes (DONE)

- **Schema/migration tracking changed this phase**: no more `.sql` files
  in the repo going forward (the user removed the Phase 2/3 migration
  files intentionally). When a phase needs a schema change, give the SQL
  directly in chat for the user to run in Supabase's SQL Editor, and
  record what changed in prose in these phase notes — don't add files
  under `supabase/`. Phase 4 itself needed no schema changes (writes only
  into tables already created in Phase 1/2's design).
- Scraper lives in `src/lib/scene/` (`fetcher.ts` + `types.ts`), ported
  from spider-bot's `fetcher.py`, parameterized by `BranchId` ('cfc' |
  'district5') rather than hardcoded to one branch. Same politeness as
  spider-bot: single browser UA, 2s delay between requests
  (`REQUEST_DELAY_MS`), never guesses slugs — only follows links found on
  `/` (now-showing) and `/next_releasing` (coming-soon).
- Real HTML gotcha found while testing against live pages (not caught by
  Phase 0's manual curl inspection): the day-selector markup nests
  `<a href="javascript:LoadShowtimes('DD-MM-YYYY')"><li class=
  "calanderdays">` — the anchor wraps the `<li>`, not the reverse. Initial
  selector (`li.calanderdays a`) silently matched zero elements and
  reported every movie as not-bookable. Fixed by selecting
  `li.calanderdays` and reading `href` off `.parent('a')` instead — caught
  only because a known-bookable movie (Spider-Man on cfc) came back
  `bookable: false` in testing, which is why this got tested against live
  pages rather than trusted from the Phase 0 write-up alone.
- `checkBookability()` returns which dates have showtimes (from the day
  selector); `fetchDayShowtimes()` hits the AJAX fragment endpoint found
  in Phase 0 (`movie-details.html?business_day=DD-MM-YYYY&ajax=1`) for
  per-showtime detail (format, time, booking URL, sold-out flag) — kept
  separate since it's one extra request per day and callers shouldn't pay
  that cost for movies they don't need showtime-level detail for yet.
- `POST /api/scrape-scene` (secret-header-protected, same pattern as
  `/api/sync-movies`) scrapes both branches' listings, and for any Scene
  slug not yet linked via `movie_branch_slugs`, creates a placeholder
  `movies` row (title from Scene, `tmdb_id` null, `match_status`
  `'unmatched'`) rather than skipping it — decided explicitly so this
  phase is fully testable end-to-end before Phase 5's TMDB matching
  exists. Phase 5 matches these placeholder rows to real TMDB entries
  instead of creating new ones.
- Verified live against both branches, twice (to check idempotency): 21
  cfc + 14 district5 listings, 15 + 8 bookable. Second run produced
  identical row counts (135 movies, 35 `movie_branch_slugs`, 35
  `showtimes_cache`) — confirms no duplicate movies/links on re-scrape.
- Confirmed the Phase 0 cross-branch slug-mismatch finding with real
  placeholder data: "Moana" ended up as two separate placeholder movies
  (`Moana (3D)` on cfc via slug `moana-english-3d-2026`, `Moana (2D)` on
  district5 via `moana-english-2d-2026`) since there's no title matching
  yet — this is expected at this phase and is exactly what Phase 5 needs
  to reconcile.
- Not yet done, deferred: no TMDB matching (Phase 5, so cfc/district5
  listings of the same movie remain separate placeholder rows until
  then), no watchlist-driven scoping (Phase 6 — this phase scrapes every
  listed movie on both branches, not just watchlisted ones, which is fine
  for proving the scraper but not the final polling shape).

## Phase 5 notes (DONE)

- **Migration/schema tracking**: per the Phase 4 change, no `.sql` files
  in the repo. Phase 5 needed no schema changes (works entirely with
  Phase 1's existing `movies`/`movie_branch_slugs`/`showtimes_cache`
  columns).
- Two-step pipeline in `src/lib/matching/`, run via
  `POST /api/match-movies` (same secret-header pattern as the other two
  jobs): `merge-scene-duplicates.ts` first, `match-to-tmdb.ts` second.
  Must run in that order — merging first means each real movie gets
  looked up against TMDB once, not once per branch it's listed on.
- `merge-scene-duplicates.ts` groups Scene placeholder movies (from
  Phase 4, `tmdb_id` null) by normalized title (`src/lib/matching/
  normalize.ts` strips `(2D)/(3D)/DUB/ARABIC/ENGLISH` suffixes), keeps the
  oldest row per group as canonical, repoints `movie_branch_slugs`/
  `showtimes_cache` onto it branch-by-branch (guards against a
  (movie_id, branch_id) collision even though today's data never
  produces one), then deletes the redundant rows.
- `match-to-tmdb.ts` implements the Phase 0/1 pipeline exactly: English
  search → Arabic fallback on zero results → disambiguate multi-result
  collisions by requiring an EG **theatrical** release_dates entry
  (`getEgTheatricalReleaseDate` in `src/lib/tmdb.ts`) → anything not
  resolved to exactly one confident candidate is left `ambiguous` or
  `unmatched`, never guessed by popularity. When a Scene row matches a
  tmdb_id that already exists as a Phase 2 row, the Scene row's slugs/
  cache get moved onto the existing row and the Scene placeholder is
  deleted; when it matches a brand-new tmdb_id, the Scene row's
  title/original_title/poster_path/release_date/popularity get
  overwritten from TMDB so every `movies` row looks the same regardless
  of which phase created it (Scene's format-suffixed titles like
  "Spider-Man: Brand New Day (2D)" don't survive into the canonical row).
- **Real bug found and fixed during result verification, not by code
  review**: the initial `getEgReleaseDate()` fell back to returning *any*
  EG release_dates entry if no theatrical one existed, rather than
  returning null. This nearly auto-matched Scene's real 2026 "Moana (3D)"
  listing to TMDB's **Moana 2** (a 2024 Disney+ release with an EG entry
  of `type: 4`/digital, no theatrical EG entry at all) — a genuinely wrong
  match that would have shown a 2024 already-released sequel as this
  year's Egypt cinema release. Caught by manually checking each auto-match
  against TMDB's raw data after the first live run, not by design review
  beforehand. Fixed by renaming to `getEgTheatricalReleaseDate()` and
  making it return `null` when no entry has `type` 2 or 3, instead of
  falling back to a non-theatrical date. Re-verified all 9 other
  auto-matches from that run against the fixed logic — all were correct;
  only Moana was wrong, and it now correctly lands as `ambiguous`.
  **Lesson for future phases**: when a heuristic can silently produce a
  wrong-but-plausible-looking answer (not an error), verify actual
  outputs against ground truth before trusting a live run, even after
  code review and a clean build/lint pass.
- Verified live against real Phase 4 data (135 movies: 100 TMDB-sourced +
  35 Scene placeholders): merge step collapsed 14 cross-branch duplicate
  groups (16 rows deleted, e.g. "The Odyssey" and "Ice Cream Man" each
  existed once per branch before merging); match step landed 9 confident
  matches (including the exact TMDB collision Phase 0 flagged — two 2026
  movies both titled "The Odyssey" — correctly resolved to the one with a
  real EG theatrical entry), 6 ambiguous, 3 unmatched. Confirmed the
  Arabic-fallback limitation Phase 0 predicted is real and unresolved:
  Scene only exposes English-transliterated titles (e.g. "Khali Balak Min
  Nafsik"), and TMDB's Arabic search needs actual Arabic script, not a
  transliteration — so these still land `unmatched` and need a different
  data source (or manual entry) to ever resolve automatically.
- Not yet done, deferred: no manual-review UI for `ambiguous`/`unmatched`
  rows (Phase 7), no re-running strategy decided for when Phase 6's
  polling discovers new Scene listings over time (this phase's route is
  safe to re-run — merge and match are both idempotent against
  already-resolved rows — but nothing schedules it yet).

## Phase 6 notes (DONE)

- `src/app/watchlist/` — minimal watchlist page + server actions
  (`addToWatchlist`/`removeFromWatchlist`). Deliberately bare-bones (a
  plain list with add/remove buttons over every `matched` movie) since
  real browse/search UI is Phase 7's job — this phase only needed enough
  UI to prove the watchlist → poll → notify loop end to end. Actions run
  through the RLS-respecting server client, so `watchlist`'s existing
  Phase 3 RLS policies (scoped to `auth.uid()`) do the actual enforcement
  — confirmed directly: a signed-in user can add/remove their own rows,
  and inserting a row with someone else's `user_id` is rejected by
  Postgres with `42501` (RLS violation), not just silently filtered.
  Duplicate add is caught via Postgres `23505` and treated as a no-op,
  same pattern as the Phase 3 ntfy-topic-collision handling.
- `src/lib/ntfy.ts` — `notifyBookable()`, message format matches
  spider-bot's `notifier.py` (title/body/booking link/checked-at
  timestamp), posted to the user's private topic from their `profiles`
  row. One deliberate deviation from a direct port: the `Title` HTTP
  header is stripped to ASCII before sending (ntfy's own docs flag
  UTF-8-in-headers as inconsistently supported across client libraries),
  while the message body keeps the real title as-is since body isn't
  subject to the same header-encoding constraint.
- `POST /api/poll` (`src/app/api/poll/route.ts`, same secret-header
  pattern as the other jobs) is the centralized poll job the whole
  project's scaling constraint depends on: it only checks (movie, branch)
  pairs that have at least one watcher (`select distinct movie_id from
  watchlist`, then joins to `movie_branch_slugs` for the known slugs) —
  cost scales with distinct watched movies, never with user count, per
  the Phase 1 architecture decision. No Vercel Cron entry — per Phase 1,
  this route is meant to be hit by an external scheduler (cron-job.org or
  similar) on a real interval; that scheduler itself isn't wired up until
  Phase 8 deploy.
- Notify-once logic: reads `showtimes_cache.bookable` *before* upserting
  the new scrape result, so it always knows the previous state. Newly
  bookable (was false/absent, now true) → notify every watcher without an
  existing `notification_log` row for that (user, movie, branch), then
  insert the log row. Transition back to not-bookable → delete all
  `notification_log` rows for that (movie, branch) across every user, so
  a future re-opening (added showtimes, re-release) notifies again rather
  than staying silently suppressed forever — confirmed with the user this
  is the wanted behavior, not "notify once ever."
- Verified live, not just typechecked: created a real test user with a
  real ntfy topic, watchlisted a real bookable movie (Spider-Man, on both
  branches), and confirmed actual push notifications arrived at the ntfy
  topic (checked via ntfy's own JSON polling endpoint) with correct title,
  branch name, and booking link. Re-polling produced zero duplicate
  notifications. The not-bookable-clears-log branch couldn't be exercised
  through a live HTTP call (Scene's real site won't go not-bookable on
  demand for a test), so that specific branch was verified by running the
  identical DB read/upsert/delete sequence directly against Supabase,
  then confirming a subsequent real poll re-notified only the (movie,
  branch) pair whose log had been cleared, not the other one — same code
  path, exercised through the actual API on the following poll.
- Also verified RLS blocks watchlisting on someone else's behalf, and that
  deleting a user (via Supabase auth admin) cascades cleanly through
  `watchlist` and `notification_log` via their FK `on delete cascade`,
  leaving no orphaned rows.
- Not yet done, deferred: no UI feedback distinguishing "already
  watchlisted" vs "just added" beyond the button swapping (Phase 7 polish
  territory), no external scheduler actually configured to hit `/api/poll`
  yet (Phase 8 — this phase only proves the endpoint itself works
  correctly when called), poll currently re-checks bookability for every
  watched (movie, branch) pair on every invocation regardless of how
  recently it was checked — fine at today's scale, but if watchlist size
  grows enough to threaten the Hobby function-duration budget, revisit
  batching/staggering rather than assuming it pre-emptively.

### Visual identity pass (post-Phase-7 follow-up)

Renamed the product from "reel-alert" to **ReelAlert** across all
user-facing text (nav wordmark, `<title>`, meta description, ntfy topic
placeholder). The app's internal package/repo name and directory are
still `reel-alert` — this is a display-name change only, not a rename of
the project itself.

Also replaced the initial generic Tailwind-defaults look (white cards,
gray badges, system sans) with a deliberate design system, since the
first pass read as templated:

- Color tokens defined once in `globals.css` as CSS custom properties
  (`--bg`, `--bg-elevated`, `--ink`, `--ink-dim`, `--rule`, `--accent`,
  `--accent-ink`, `--ok-bg`/`--ok-ink`, `--listed-bg`/`--listed-ink`),
  redefined under `@media (prefers-color-scheme: dark)` and mirrored
  under `:root[data-theme="dark"]`/`:root[data-theme="light"]` for an
  explicit toggle if one's ever added. Components reference tokens via
  inline `style` (not hardcoded Tailwind gray/neutral utility classes),
  so the palette lives in exactly one place.
- Warm near-black ground in dark mode (`#0e0d0f`, not blue-black) and
  warm paper in light mode (`#faf8f4`, not pure white), both paired with
  one marquee-red-orange accent (`#d1450f` light / `#e8622f` dark, kept
  more saturated in dark mode so it still reads against the dark ground)
  used only for the wordmark, primary actions, and links — never as a
  background flood. **Superseded by the palette rescheme below** — kept
  here for history, not current.
- Typography: `Bebas Neue` (tall condensed display face, evokes marquee/
  poster lettering) for the wordmark and every movie title, paired with
  `Inter` for UI chrome and body text. Both loaded via `next/font/google`
  in `layout.tsx` (self-hosted at build time, no runtime font-CDN call).
- `MovieCard` and the watchlist list item both got a `.poster-card` hover
  lift (`translateY` + shadow, gated behind
  `prefers-reduced-motion: no-preference`) suggesting a lit poster case
  rather than a flat SaaS card.
- Verified again in an actual browser (Playwright, both color schemes)
  after the redesign, not just visually inspected in isolation — same
  approach as the original Phase 7 verification.

### Scene-brand palette rescheme + movie detail pages + bookable filter

Replaced the marquee-red-orange accent above with Scene Cinemas' actual
brand colors, and added the two features the user asked for on top:

- **Palette now matches Scene Cinemas' own branding**, pulled directly
  from `cfc.scenecinemas.com`'s real theme stylesheet rather than
  guessed: primary `#00534c` (deep teal, used 13x across Scene's buttons/
  showtime-selection states — unambiguously their brand color), paired
  with a `#3ddacc` mint used the same way Scene uses it (active/selected
  state highlight, not a base color) — now the `--highlight` token, and
  the dark-mode `--accent` (more saturated against a dark ground than the
  light-mode teal would be). Light mode uses a cool off-white/pale-teal
  ground instead of the previous warm paper, to sit correctly next to a
  teal accent rather than fighting it.
- **Caught a real bug while reschemeing, not introduced by it**: three
  auth pages (`signin`, `signup`, `account`) had a hardcoded dark-mode-only
  error message color pair (`#3a1810` background / `#f3a58a` text) applied
  unconditionally — meaning error messages would have rendered
  dark-on-dark styling even in light mode. Never actually seen broken
  because no one had triggered a real error in light mode during earlier
  testing. Fixed by adding proper `--error-bg`/`--error-ink` tokens to the
  palette (themed correctly for both modes) and switching all three pages
  to reference them.
- **Movie detail pages** at `/movies/[id]` (keyed on the internal
  `movies.id`, not `tmdb_id`, so even the 5 rows with no TMDB match at all
  still get a page): full-bleed backdrop with a gradient fade into the
  page background, overlaid poster, tagline, overview, runtime, genres,
  director + cast grid (circular photos, Letterboxd-style), and a
  showtimes sidebar per branch with real showtime dates and a
  "Select showtime on Scene" link that sends the user to Scene's actual
  booking flow — this app never automates ticket purchase, matching the
  constraint that's held since Phase 0.

### Replaced ntfy.sh with browser push notifications

ntfy required installing a separate app and manually typing a shared
topic name to connect it — real friction the user wanted gone. Replaced
outright (not kept alongside) with standard Web Push (VAPID), which
needs nothing beyond a browser permission prompt.

- **`src/lib/notifications.ts`** is new: `BookableNotification`/
  `NewReleaseNotification`/`formatCheckedTimestamp` moved here from the
  now-deleted `src/lib/ntfy.ts`, since `email.ts` depended on those

  `ntfy.ts` itself was deleted.
- **`src/lib/push.ts`** replaces `ntfy.ts`: `notifyBookablePush()` /
  `notifyNewReleasePush()`, built on the `web-push` npm package (VAPID),
  no third-party push service in the loop. A user can have multiple
  subscriptions (one per device/browser they've enabled push on); both
  functions fan out to every row in `push_subscriptions` for that user.

  (ntfy topics don't expire the same way).

  shows a notification via `showNotification`, `notificationclick`
  focuses an existing tab on the booking URL or opens a new one).

  page load — only when a user actually opts in.

  client component) owns the whole lifecycle: checks for existing
  subscription on mount, requests `Notification.requestPermission()`,
  registers the service worker, subscribes via `pushManager.subscribe()`
  with the app's VAPID public key, and POSTs the resulting subscription
  to the new `/api/push/subscribe` route. Renders one button whose
  label/action flips between subscribe/unsubscribe based on actual
  browser state (not a DB flag), and a plain explanatory sentence
  instead of a button when push isn't supported or was already denied
  at the OS/browser level (denial can't be un-prompted from JS, the
  user has to fix it in site settings themselves).
- **`/api/push/subscribe`** and **`/api/push/unsubscribe`**
  (`src/app/api/push/`) are RLS-respecting server routes (the ordinary
  cookie-auth client, not service-role) that upsert/delete rows in the

  policy rather than only in the route handler.

Closed out the "not yet verified live" gap above. Getting a real

### Theme-switch animation, full mobile audit

- **Theme switching felt abrupt** (real user complaint after the
  toggle shipped): every CSS custom property (`--bg`, `--ink`,
  `--accent`, etc.) flipped instantly with no transition, so the whole
  page's colors snapped on click. Fixed with one global rule in
  `globals.css` — `*, *::before, *::after { transition: background-
  color, border-color, color, fill, stroke 0.25s ease }` — scoped to
  color-related properties only (not `all`, which would also animate
  layout properties like width/height on every element, a real jank/
  perf risk) and gated inside the existing `prefers-reduced-motion:
  no-preference` block, same convention as every other animation in
  this file. This one rule is what makes the transition apply
  app-wide at once: every component consumes the theme tokens via
  inline `style={{ background: 'var(--bg)' }}`-style props rather than
  a shared class, so a per-component transition would've meant editing
  every component individually.
  - `ThemeToggle`'s icon swap also got its own small animation
    (`theme-icon-swap`: fade + slight rotate-in, 0.28s), using a
    `key={preference}`-forced remount so the keyframe replays on every
    click rather than only running once.

    Playwright check clicked the toggle and listened for an actual
    `transitionend` event on `document.body`, confirming it fires at
    exactly the declared `0.25s` and the background color genuinely
    changes. Separately confirmed `prefers-reduced-motion: reduce`
    correctly disables it (`transition-duration` computes to `0s` in
    that context) rather than just trusting the media query was
    written correctly.
- **Full mobile audit across every route**, prompted by the earlier
  nav-wrap bug only having been caught on `/browse` specifically

### VOX Cinemas added as a second cinema chain

- `https://elcinema.com/en/theater/3101353/` = Vox City Centre Almaza Cinema

lists every currently-showing movie with its real VOX slug and title.

(confirmed, full contents):

```
User-agent: *
Disallow: */booking/
Disallow: */account/
Disallow: */terms-and-conditions
Disallow: */terms-of-use
Disallow: */privacy
Disallow: */Anti-Fraud-Disclaimer

User-agent: AASA-Bot
```

`/booking/` and `*?*` (any query string) are both disallowed under
`User-agent: *`. This app's rule since Phase 0 has been "respect
robots.txt, no exceptions," so per-showtime `/booking/...` links are
never fetched or stored by this app at any layer, confirmed off-limits
with no exception carved out. A day-specific `?d=...` link was
initially planned as a plain `<a href>` for a human to click (robots.txt
governs this app's own automated fetching, not what URL a page links to
for a person to open themselves) — this reasoning held up, but the
actual VOX-slug-discovery mechanism needed to build such a link (see
Round 5) was later shelved for unrelated infrastructure reasons, so this
specific link shape never shipped; see "booking-link redesign" below for
what did.

**Round 5 — the Playwright/Vercel dead end.** The original plan called
for a small Vercel serverless route (`/api/scrape-vox-slugs`) running
Playwright to discover VOX's own movie slugs from the allowed
`/movies/whatson`/`/movies/comingsoon` pages, using
`@sparticuz/chromium-min` (the standard way to run headless Chromium on
Vercel within its function size limits) + `playwright-core`. Two real
deploy-time bugs were found and fixed via a real Vercel preview
deployment (deployment protection for Preview deployments was disabled
to allow direct testing):
1. `Cannot find module '.../playwright-core/browsers.json'` — Next's
   automatic file tracing didn't include the package's non-JS assets for
   this route. Fixed via `outputFileTracingIncludes` in `next.config.ts`.
2. **The real, unfixable blocker**: with that resolved, the route got
   past module loading and launched the browser, but
   `page.goto('https://egy.voxcinemas.com/')` failed with
   `net::ERR_HTTP2_PROTOCOL_ERROR` — the exact same failure Akamai gave
   every *headless* attempt during Round 1. Root cause, confirmed by
   reading `@sparticuz/chromium-min`'s own source (literal comment: "We
   only support running chrome-headless-shell"): this package only ever
   launches `chrome-headless-shell`, a distinct, more easily
   fingerprinted Chromium build than the regular headed Chromium that
   worked in Round 3 — a hard architectural limitation of the package,
   not a launch-flag or config fix. Confirmed there's no realistic
   alternative package bundling full Chrome/Chromium small enough to fit
   Vercel's function size limits.

**Round 6 — Browserless.io investigated, then dropped.** The decided
path forward (with the user, at the time) was to switch to a remote
browser service — real full Chrome running on someone else's
infrastructure, reached via `chromium.connectOverCDP(wsEndpoint)`
instead of bundling a binary. Browserless.io was the candidate, with a
`/chromium/stealth` endpoint aimed specifically at this kind of bot
detection. Work paused when Browserless.io's signup wasn't working for
the user; a checkpoint was written into `CLAUDE.md`/this file so a future
session could resume without re-deriving the investigation. **When
picked back up, the user explicitly shelved this whole approach instead
of resuming it** — not worth adding a new managed third-party dependency
(this project has otherwise stayed entirely free-tier/self-hosted) for
one link's precision. `scrape-vox-slugs` was deleted outright, along
with `playwright-core`/`@sparticuz/chromium-min` and the
`outputFileTracingIncludes` config entry. **Final decision: this app's
server never touches VOX's own site at all.** Every VOX booking link
initially shipped as the bare homepage (`VOX_HOMEPAGE_URL` in
`src/lib/branches.ts`).

**Round 7 — a real per-branch link found after all, without any
scraping.** In a later follow-up, the user found VOX's site has real,
static, per-branch showtime URLs
(`egy.voxcinemas.com/showtimes?c=mall-of-egypt` etc.) just by browsing
it normally. Since there are only 3 branches and their slugs are static
(`mall-of-egypt`, `city-centre-alexandria`, `city-centre-almaza`,

`VOX_BRANCH_SLUGS`/`voxBranchShowtimesUrl()` in `src/lib/branches.ts` —

movie-level slug discovery. Same robots.txt reasoning as Round 4 applies
(query string, but only ever placed as a link for a human to click, never
fetched by this app's own server). Wired into the movie detail page,
`WatchlistGrid`, and both `/cinemas` pages, replacing the bare
`VOX_HOMEPAGE_URL` wherever a specific branch context was available.

**Round 8 — real VOX showtimes on the movie detail page.** Originally
`scrape-vox` only persisted a bookable-date list into
`showtimes_cache.raw_showtimes` for VOX rows (discarding the actual
per-format/per-time/per-price detail `fetchVoxShowtimes` already
returns), and the movie detail page just showed a generic outbound link
for VOX branches. Changed `scrape-vox` to persist the full detail
instead — a new `VoxDayDetail` shape
(`{date, formats: [{format, showtimes: [{time, price}]}]}`) stored in
the same `raw_showtimes` jsonb column Scene uses for its own, differently

renders it on the movie detail page: day tabs (reusing the existing
`DateTabStrip`) plus real times/formats/prices per day, all already
loaded from the DB (no per-click fetch, unlike Scene's `ShowtimePicker`
— elCinema has no cheap partial-detail endpoint to defer to, so
`scrape-vox` already fetches everything upfront). Each time slot links
out via `voxBranchShowtimesUrl()`, not a specific showtime (still
robots.txt-disallowed per Round 4). New ISO-date helpers
(`parseIsoDate`/`filterFutureIsoDates`/`formatIsoDateLabel` in
`src/lib/scene/dates.ts`) sit alongside the existing Scene `dd-mm-yyyy`
versions rather than one shared parser guessing at input shape.

**Two real bugs surfaced by this shape change, on pages outside the
immediate task's scope, caught only by re-testing broadly rather than
by the type checker** (the `raw_showtimes` column is loosely typed
`unknown`/cast at each call site, so nothing statically enforced a
consistent shape across chains): `src/app/cinemas/[id]/page.tsx` crashed
outright (`date.split is not a function`) trying to parse a VOX row's
new object-shaped `raw_showtimes` through Scene's `parseSceneDate` in
its date-tab-picker aggregation logic — fixed by skipping that
aggregation entirely for `branch.chain === 'vox'` (the UI it feeds,
`CinemaMovieGrid`'s date picker, was already Scene-only anyway, so this
is a no-op for VOX, not a missing feature). `src/components/WatchlistGrid.tsx`
would have silently rendered `[object Object]` in its inline "(dates...)"
list for the same reason — fixed by gating that span on
`chainForBranch(...) !== 'vox'` too, same pattern. **Lesson for future
schema/shape changes to a shared column: grep the whole repo for every
consumer before considering the change done, not just the files already
open for the current task** — both bugs were found by deliberately
re-testing pages adjacent to, but not part of, the original task scope.

**Browse page redesign** (a separate, related follow-up request in the

## Notification end-to-end test on real users, custom domain purchased

Two things happened in this session: a real notification test against
live watchers, and the start of a custom-domain migration meant to
finally unblock the long-standing Resend email limitation.

**Notification test (two attempts, both reverted cleanly)**. The user
wanted to see the actual notify flow fire for real, not a mocked test --
specifically wanted "The End of Oak Street" forced bookable at District 5
with its booking link swapped for an arbitrary YouTube URL, to visually
confirm what a real notification looks like end to end. Real production
data was involved (the movie has two genuine watchers:
`belalhamada489@gmail.com` and `dommawalid@gmail.com`), so the approach
was explicitly discussed with the user first rather than assumed --
offered a "me-only, no real DB writes" script as the safer default, but
the user chose the real path (flip real `showtimes_cache` state, run the
actual `/api/poll` route, notify real watchers) both times it was run.
Mechanism used, twice, identically: a narrowly-scoped temporary override
block added directly in `src/app/api/poll/route.ts`'s Scene branch (`if
(row.movie_id === '<the-end-of-oak-street-id>' && branch === 'district5')
{ bookable = true; bookingUrl = '<youtube-url>' }`), placed after the real
`checkBookability()` call so it overrides the live (false) result rather
than skipping the real scrape -- run via `curl -X POST /api/poll` against
a local `npm run dev` instance -- then fully reverted immediately after
confirming: the code block removed, `showtimes_cache.bookable` reset back
to `false` for that movie/branch, and the `notification_log` rows the
test created deleted, each time confirmed via direct Supabase queries
(service-role client, ad hoc `node -e` scripts since no test-fixture
scripts exist for this) rather than assumed. `git status` confirmed clean
after each revert.

**Real finding, not a bug in this app**: only `belalhamada489@gmail.com`
(the Resend account's own signup address) actually received the email
both times; `dommawalid@gmail.com` did not. Root-caused directly via a
raw call to Resend's `/emails` API (bypassing this app's own
try/catch-swallowed error handling, which is why the failure was
invisible in the poll route's own logs) -- Resend returned a `403
validation_error`: *"You can only send testing emails to your own email
address... verify a domain... and change the `from` address."* This is
exactly the pre-existing, already-tracked "email delivery is NOT live for
real users" gap, now confirmed with a concrete reproduction rather than
just a general awareness that it was unverified. Retrying the send
against the same recipient (at the user's request, to double-check it
wasn't transient) reproduced the identical 403 -- confirmed this is a
permanent account-level sandbox restriction, not a flaky send.

**Custom domain purchased to resolve this**: user bought
`reelradar.online` from Hostinger. Two independent DNS setups needed on
the same domain, explained as separate tracks since they're easy to
conflate: (1) pointing the domain at Vercel for web hosting (A record
`@` -> Vercel's apex IP, optionally `www` via CNAME to
`cname.vercel-dns.com`), and (2) verifying the domain with Resend for
email sending (TXT/CNAME/MX records Resend's dashboard generates per-
domain, added in the same Hostinger DNS Zone Editor alongside the Vercel
records -- different record types/names, so they coexist without
conflict). **Vercel side confirmed live** by direct check (not just
assumed from the user saying "done"): `nslookup reelradar.online`
resolves to a real Vercel edge IP, `curl -I https://reelradar.online`
returns `200` with `Server: Vercel` and a valid HSTS header: the app is
genuinely being served there. **Resend side is still pending** -- the
user had said "done" but on follow-up clarified DNS records are still
outstanding on Resend's side (a real case of "done" meaning one of two
bundled steps, not both -- worth explicitly re-confirming rather than
assuming "done" covers everything asked). Attempted to verify Resend's
domain status via its `/domains` API endpoint directly rather than take
the user's word for it, but the API key in `.env.local` is
send-permission-only (`restricted_api_key`, 401) -- can't check
programmatically with the current key, so this remains user-reported
until either the key's permissions change or the user confirms via
Resend's own dashboard.

**Explicit decision deferred, not yet made**: whether `reelradar.online`
becomes the sole production URL (requiring `NEXT_PUBLIC_SITE_URL` and any
other hardcoded references to `reel-radar-ebon.vercel.app` to be swept
and updated) or the Vercel subdomain stays as a live alias alongside it.
Nothing in the codebase has been changed for the domain migration yet --
deliberately held back until Resend's verification actually completes,
since flipping `RESEND_FROM_EMAIL` to a `reelradar.online` address before
that domain shows "Verified" in Resend would break the one email channel
that currently works (delivery to the account's own address) for zero
gain.
